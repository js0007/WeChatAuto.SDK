
# 为什么选择 WeChatAuto.SDK

## 一句话定位

> **WeChatAuto.SDK 是一款安全构建微信 Agent 的开发基座**——不注入（内存 Hook）、不破解数据库、不越权访问微信数据，基于 **UI Automation + OCR 视觉混合方案**操作真实微信客户端，让你用最少代码、最快速度，把微信能力接入自己的业务。

---

## 微信自动化的三个老大难

| 痛点 | 传统做法的代价 |
|---|---|
| **安全与合规** | 内存 Hook / 协议破解 / 数据库解密，极易触发微信风控、封号，且处于灰色地带 |
| **易碎难维护** | 微信一升级，Hook 点、协议、控件路径全部失效，需要不断逆向跟进 |
| **上手门槛高** | 逆向工程、协议分析、控件定位繁琐，业务团队难以快速落地 |

这三点，恰好是 WeChatAuto.SDK 用「**模拟真人操作**」这条正路绕开的。

---

## 核心优势：安全第一，不 Hook、不破解

- **不注入（内存 Hook）**：不改写微信进程内存，不加载第三方模块进微信进程。
- **不破解数据库**：不解密、不越权读取微信本地数据。
- **不越权访问数据**：所有能力都通过 **UI Automation（FlaUI UIA3）+ OCR 视觉** 双引擎，模拟真人在微信界面上「看」和「点」来完成。

> 原理决定了它更稳、更干净：微信更新后，绝大部分能力仍然可用；即使个别控件变化，也只需维护 UI 定位而非整套逆向方案。

## 工程化打磨：为「稳定上生产」而生

### 专有线程模式：监听与发送互不抢鼠标、抢窗口

微信 UI 自动化有个隐蔽的坑：**监听任务**（新消息监听、好友申请监听）和**发送任务**如果并行执行，会同时去抢鼠标和窗口焦点、互相打断，导致「抢鼠标」「抢窗口」失败。**多微信同时在线**、或**单微信做群发**时，这种情况尤其容易发生。

WeChatAuto.SDK 从架构上直接规避了它：

- **一条专用 Action 线程**：无论开了几个微信，所有 UI 操作统一调度到同一条专用线程串行执行——宁可稍慢一点，也要保证每一步都稳定完成，而不是多个线程抢来抢去。
- **监听统一排队**：所有自动监听任务受同一把信号量（`SemaphoreSlim(1,1)`）约束，与发送操作互斥、顺序执行，天然不会和发送抢鼠标、抢窗口。

**效果**：监听与发送、多个微信之间自动排队，不抢鼠标、不抢窗口、不互相打断——这是「稳定可用」和「跑着跑着就乱套」的分水岭。

### 强开 UI Tree：微信不公开 UI Tree 也能自动化

微信默认并不公开 UI Tree（UIA 树），常规 UI 自动化方案在拿不到 UI Tree 时会直接失效。WeChatAuto.SDK 内置了「**强开 UI Tree**」能力：

- 定位 `weixin.dll` 中的门控字节并写入，让微信暴露 UI Tree，从而继续 UI 自动化；
- 过程中有可视化的进度提示，状态清晰可见。

**效果**：不依赖微信是否「开放」，兼容性更强；即使某个微信版本改了控件，也只是维护 UI 定位，而非整套逆向方案。

更多的关于让微信开放UI Tree的功能，请参见[我的最新版微信没有开放没有UI Tree怎么办？](https://github.com/scottfly189/WeChatAuto.SDK/issues/3)

### 远程桌面支持：云服务器 / RDP 上稳定运行

UI 自动化最怕远程桌面：RDP 窗口最小化或断开时会挂起远端显示缓冲，导致自动化**拿不到画面、投不进输入**。WeChatAuto.SDK 做了针对性适配：

- **禁用 RDP 最小化挂起优化**（`RemoteDesktop_SuppressWhenMinimized`），最小化远程桌面也不中断自动化；
- **会话转移**：支持把 RDP 会话转回控制台会话（`tscon`），关掉远程桌面后会话仍保持解锁、桌面继续渲染；
- **自动恢复分辨率**：避免会话转移后回落成 1024×768 导致图像识别、坐标定位失败。

**效果**：可以放心最小化远程桌面、关闭远程桌面客户端，而不用担心「人一断开，机器人就停了」。

## 为 AI Agent / LLM 时代而生

- **事件驱动**：好友申请、新消息监听都通过回调/Channel 推给你，天然适合接 LLM 做自动应答。
- **TTS 语音**：内置阿里千问（Qwen）语音合成，文字直接变微信语音发出去，语音交互 Agent 开箱即用。
- **多语言开放**：核心库之外，提供 7 个语言的官方客户端（.NET / C++ / Go / Java / Node.js / Python / Rust），任何技术栈都能接。

## 两种使用方式，按需接入

| | 内嵌方式 | HTTP WebAPI 方式 |
|---|---|---|
| 适合 | .NET / Windows 原生应用，需要事件回调、低延迟、完整 API | 后端/云服务、跨语言、多系统共享、快速集成 |
| 入口 | `WeAutomation.Initialize(...)` → `WeChatClientFactory` → `WeChatClient` | 启动 Server，REST + Swagger，`http://<主机>:5000` |
| 特点 | 类型安全、能力最全、深度定制 | 语言无关、进程隔离、可远程、开箱即用 |

> 绝大多数场景推荐 HTTP WebAPI 方式；需要 dll 内嵌、深度回调时选内嵌方式。

## 安全与风控：把「像人」做到硬件级

高频自动化最大的风险是微信风控。WeChatAuto.SDK 除了软件模拟，还支持**键鼠模拟器（硬件级输入）**：

- 通过硬件底层发信号，模拟出的输入与人手操作无异，**不留软件注入痕迹**；
- 在高敏感场景（如群内加好友）实测能有效**降低被风控概率**。

> 配合「控制频率、避免短时间批量操作」等规范用法，可获得更稳定、更安全的自动化体验。

## 快速开始（30 秒上手）

```bash
# 内嵌（.NET）
dotnet add package WeChatAuto4x.SDK
```

```csharp
var sp = WeAutomation.Initialize(o => o.EnableOCR = true);
using var factory = sp.GetRequiredService<WeChatClientFactory>();
var client = factory.GetWeChatClient("你的微信名");
await client.SendMessage("好友昵称", "hello world!");
```

```bash
# HTTP 方式：启动 Server 后，任何语言都能调用
curl http://localhost:5000/api/v1/clients
curl -X POST http://localhost:5000/api/v1/clients/<wxid>/messages/send \
  -H "Content-Type: application/json" \
  -d '{"who": "好友昵称", "message": "你好"}'
```
